# 00｜现有项目与 Figma 审计

审计日期：2026-09-20

## 1. 结论

V1 已经验证了产品心智与三类协作流程，并沉淀了一套可靠的领域规则；但它仍是单设备、浏览器本地数据的静态应用。V2 应复用“规则、术语、测试和品牌”，重建“应用架构、身份、数据、协作、通知、PWA、AI 和分析”。

## 2. GitHub / V1 现状

仓库：<https://github.com/shihongfei256-alt/hezu-life-manager-demo>

- 技术形态：原生 HTML/CSS/JavaScript ES Modules，无构建框架，Hash 路由。
- 发布目录：`docs` 与 `dist` 当前内容一致，适配 GitHub Pages 子路径。
- 持久化：`localStorage`，主键为 `hezu-life-manager:v3:state`。
- 身份：同一浏览器内切换示例室友，不是真实账号和跨设备协作。
- 数据恢复：包含临时写入恢复、备份、v2 迁移和损坏数据回退。
- 最新远端提交只把 README 中“静态网页 Demo”改成“静态网页”，未改变业务代码。
- 当前本地业务与存储测试共 26 项，全部通过。

### 已验证的领域能力

- 四种费用分摊方式，整数分守恒。
- 全屋净余额恒为零；作废费用不参与余额。
- 结算可覆盖多笔费用，支持部分结算与多人分别结算。
- 家务按自然周派生逾期，周期完成后轮换并生成下一轮，支持明确转交。
- 用品低库存认领、取消认领、入库；采购只生成一笔共同费用。
- 首页、本月、本周等时间口径已有测试。

### 不适合作为 V2 基座的部分

- 全量状态保存在一个本地对象中，没有真正的用户、权限、并发与审计边界。
- UI 由命令式 DOM 拼接构成，功能继续增长后难以维护状态、路由和组件一致性。
- 没有服务端事务、幂等、防重复提交和并发冲突处理。
- 没有真实邀请、云同步、系统通知、对象存储、PWA、AI 或产品分析。
- 示例身份切换容易让演示数据与真实账号能力混淆。

## 3. Figma 现状

设计文件：[搭子屋｜合租生活管家 App 原型 v1](https://www.figma.com/design/jNZq9eZOepmL1ZivH91hSA/%E6%90%AD%E5%AD%90%E5%B1%8B%EF%BD%9C%E5%90%88%E7%A7%9F%E7%94%9F%E6%B4%BB%E7%AE%A1%E5%AE%B6-App-%E5%8E%9F%E5%9E%8B-v1)

- 8 张 390×844 高保真画面：今天、费用、家务、用品、新增费用、分摊核对、家务完成、更多。
- 视觉基础：深海军蓝、暖黄、纸感底色、细边框、白卡片、克制阴影。
- 底部 4 个主目的地对应真实的同级任务，因此保留 TabBar 有充分理由。
- 假系统状态栏已去除，底部系统手势条已隐藏；正式 Web App 使用安全区变量，不重画系统界面。
- 分摊示例满足金额守恒：¥7.98×2 + ¥7.97×2 = ¥31.90。
- 当前为静态设计稿。选中画板组后，Prototype 面板没有已配置交互；不能把它称作可点击原型。
- 页面目前分为两组嵌套画板。下一轮应把业务屏幕整理为顶层画板，再逐条连通主流程。

### Figma 可直接继承

- 品牌识别与配色角色。
- “今天”作为个人行动中枢的核心心智。
- 费用核对单、家务完成反馈、用品缺货优先等信息层级。
- 真实中文内容、非装饰性图标、44px 以上触控区、红色只用于风险。

### Figma 必须补齐

- 登录、创建/加入小屋、邀请与成员权限。
- 费用详情、结算发起、收款方确认、撤销/冲正和历史追溯。
- 家务转交接收、提醒设置、冲突/重复提交状态。
- 用品认领、采购录入、关联费用的完整成功与失败状态。
- 通知、活动记录、规则版本、离线、加载、空状态、错误、权限不足。
- AI 输入、解析中、候选操作、字段纠错、确认、执行结果和失败恢复。

## 4. 复用矩阵

| 资产 | V2 处理 |
| --- | --- |
| 产品名称、术语、品牌主色 | 继承并形成设计令牌 |
| 费用/家务/用品的纯业务函数 | 迁移为 TypeScript domain package，先保留行为测试 |
| 26 项测试场景 | 转成 V2 的回归基线并扩充并发、权限、幂等测试 |
| 示例数据 | 仅作为开发 fixture，明确标注，不进入产品分析 |
| `app.js` 命令式 UI | 不迁移 |
| `localStorage` 状态模型 | 仅用于理解字段；不作为云端 schema |
| Figma 八页 | 作为视觉与关键流程起点，不机械复刻 |
| GitHub Pages 部署 | V1 保留；V2 改用支持服务端能力的部署链路 |

## 5. 设计方向

采用“可信的共享生活工作台”：标准密度、 polished finish、适度活力、中等视觉重量、友好但不幼稚。海军蓝负责结构与可信度，暖黄只标记需要行动的节点，纸感底色让费用和规则像可追溯的生活记录。

不使用霓虹、紫蓝渐变、廉价玻璃、装饰性 3D、Emoji 导航、超大圆角堆叠或为了填空而增加的卡片。页面留白必须形成阅读节奏；当内容较少时使用有明确下一步的空状态、摘要或活动记录，而不是留下无目的的大块空白。
